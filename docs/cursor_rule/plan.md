# План реализации AgFlow

Цель: полностью форкнуть и ребрендировать Activepieces в AgFlow (agflow.ru), внедрить собственный биллинг (YooMoney, СБП, карты через PSP), сохранить UI-стили, настроить инфраструктуру и деплой на TimeWeb VDS. План опирается на требования и архитектурные правила проекта.

## Принципы
- Следовать монорепо NX, TypeScript strict, Fastify API, Redis + BullMQ, PGLite по умолчанию.
- Не менять цветовые токены Tailwind; заменить только названия и логотипы.
- Платёжные потоки строго идемпотентны, вебхуки подписаны и верифицированы.
- Все изменения сопровождаются миграциями, тестами, бэкапами и инструкциями по откату.

## Этапы реализации

### Этап 0 — Аудит и подготовка
- Провести инвентаризацию брендинга: найти упоминания Activepieces (названия, URL, assets, CDN).
- Согласовать ветвление и рабочие ветки: `chore/branding`, `feat/billing`, `feat/fx`, `feat/subscriptions`, `ops/deploy`, `ops/backup`.
- Подготовить список требуемых секретов и конфигов (см. раздел «Секреты и конфигурация»).
- Результаты: список мест замены бренда, перечень секретов, план ветвления.

### Этап 1 — Ребрендинг
- Заменить логотипы и текстовые упоминания на AgFlow; удалить ссылки на Activepieces cloud/API.
- Обновить README, лицензию (если требуется), ссылки на домен `agflow.ru`.
- Не изменять темы/цвета Tailwind; проверить визуальную целостность UI.
- Результаты: единый бренд, чистый репозиторий без внешних зависимостей на Activepieces.

### Этап 2 — Базовая конфигурация окружения
- Добавить пример `dev.env` и проверить локальный запуск; обеспечить `docker-compose.dev.yml`.
- Настроить PGLite: путь хранения данных в volume, `DATABASE_URL=file:./data/agflow_pglite.db`.
- Настроить Redis и Worker; проверить соединения.
- Подключить Sentry (DSN из секретов); включить базовые метрики `/metrics` (опционально).
- Результаты: воспроизводимое dev-окружение, работающий API/Worker, мониторинг ошибок.

### Этап 3 — Архитектура биллинга
- Создать модуль `packages/server/api/src/services/billing`.
- Определить интерфейс `BillingProvider` и реализовать модели: `Payment`, `Invoice`, `Subscription`.
- Добавить аудит-лог для платежных событий; репозитории для работы с БД.
- Результаты: каркас биллинга и типобезопасные интерфейсы.

### Этап 4 — Платёжные провайдеры
- Реализовать `YooMoneyProvider` и `SBPProvider`; адаптер для карт через PSP.
- Методы провайдеров: `createPayment`, `checkPayment`, `webhookHandler`.
- Вебхуки: Fastify-роуты `/api/billing/webhook/*`, верификация подписи, идемпотентность, транзакционность.
- Результаты: рабочие интеграции YooMoney и СБП, каркас для PSP.

### Этап 5 — FX сервис (конвертация в RUB)
- Реализовать `fxService` с кэшированием в Redis (TTL 3600 сек, конфигурируемо) и фолбэком на прошлое значение.
- Эндпоинт `GET /api/billing/convert?amount=XX&from=USD&to=RUB`.
- Результаты: надежная конвертация валют с кэшем и устойчивостью к отказам.

### Этап 6 — Прайсинг и UI
- Модель тарифов: Free (200 кредитов разово), Professional (1290 ₽/мес), Standard (490 ₽/мес), Enterprise (кастом).
- Эндпоинт превью цены: учитывает тариф, Flows Usage, AI Credits, FX-конвертацию, округление до копеек.
- UI-страницы: `/billing`, `/settings/billing`; модальные окна «Купить кредиты», «Купить потоки»; «История платежей».
- Результаты: пользователь может рассчитать и совершить покупку; история видна в аккаунте.

### Этап 7 — Подписки и задания
- Эндпоинты подписок: создать, отменить, просмотреть; дополнительные рекуррентные счета при отсутствии поддержки у провайдера.
- Ежедневная reconcile-задача: проверка статусов подписок у провайдеров.
- Блокировки/конкурентность: транзакции в БД, Redis-локи при изменении балансов.
- Результаты: стабильные подписки, консистентные балансы.

### Этап 8 — Учёт использования и квоты
- Таблица `usage_records` для учёта потоков и AI-кредитов.
- Планировщик перерасчёта и применения лимитов; блокировка старта новых потоков при превышении квоты, апселл.
- Результаты: корректное ограничение использования согласно плану.

### Этап 9 — Уведомления
- Email-уведомления: платёж успешен/неуспешен, счёт создан, подписка истекает.
- In-app уведомления центра событий биллинга.
- Результаты: пользователи информированы о ключевых событиях.

### Этап 10 — Тестирование
- Unit-тесты: `BillingService`, прайсинг, FX.
- Интеграционные: обработка вебхуков YooMoney/SBP, идемпотентность.
- E2E: покупка → вебхук → обновление баланса; покрытие ≥80% для критичных модулей.
- Результаты: проверенная надёжность критичных сценариев.

### Этап 11 — База данных и миграции
- Начальные миграции: схемы `plans`, `invoices`, `payments`, `subscriptions`, `usage_records`, `audit_logs`.
- Скрипты отката для каждой миграции; тесты миграций на staging.
- Инициализация PGLite для новой инсталляции; документация по переносам.
- Результаты: миграции готовы, откаты документированы, тесты пройдены.

### Этап 12 — Бэкапы и восстановление
- Скрипты: `scripts/backup_db.sh`, `scripts/restore_db.sh`; ежемесячный фулл-бэкап, хранить последние 3 копии.
- Проверка целостности бэкапов; пробные восстановления на тестовой среде.
- Результаты: надёжная стратегия резервирования и восстановления.

### Этап 13 — CI/CD
- GitHub Actions: lint, build, tests на PR; сборка Docker-образов на `main`.
- Релизы: теги образов, changelog; секreты в GitHub Secrets.
- Результаты: автоматизированная проверка качества и сборка.

### Этап 14 — Деплой на TimeWeb
- `docker-compose.prod.yml`, конфиг Nginx (reverse proxy + SSL), `scripts/deploy_prod.sh`.
- Стратегия нулевого простоя; smoke-тесты после деплоя.
- Результаты: воспроизводимый продакшн-деплой.

### Этап 15 — Наблюдаемость и алертинг
- Sentry для ошибок; метрики Prometheus (опционально); алерты: сбои платежей, рост бэклога очереди.
- Результаты: оперативное обнаружение проблем.

### Этап 16 — Документация
- Подготовить и обновить: `run-local.md`, `deploy.md`, `payment_providers.md`, `backup_and_restore.md`, `migrations.md`, `admin_guide.md`, `api_reference.md`.
- Результаты: полная документация для эксплуатации и поддержки.

### Этап 17 — Роллаут и поддержка
- Стейджинг с тестовыми ключами провайдеров; пошаговый запуск платежей.
- Контакты поддержки, инцидент-рутборд, SLA для enterprise.
- Результаты: безопасный выход в прод и поддержка пользователей.

## Секреты и конфигурация (минимальный набор)
- `AP_DB_TYPE`, `DATABASE_URL`, `REDIS_URL`, `JWT_SECRET`.
- `YOOMONEY_CLIENT_ID`, `YOOMONEY_SECRET`, `SBP_PROVIDER_KEY`.
- `FX_API_URL`, `FX_API_KEY` (может быть пустым для публичного API).
- `SENTRY_DSN`, `PAYMENT_CURRENCY=RUB`, `DOMAIN=agflow.ru`.
- Политика: секреты только в окружении/Secrets, не коммитить.

## Контрольные списки

### Pre-commit/PR
- Conventional Commits; обновить/добавить тесты; пройти lint/build/tests.
- Проверить отсутствие утечек секретов и платёжных данных в коде/логах.

### Pre-merge
- Code review по идемпотентности, транзакциям, валидации входов.
- Проверка миграций и откатов; покрытие тестами критичных путей ≥80%.

### Pre-deploy (TimeWeb)
- Настроены переменные окружения; Redis/DB доступны; SSL валиден.
- Провайдеры платежей зарегистрировали вебхуки; запущены контейнеры `up -d --build`.
- Выполнены миграции; пройдены smoke-тесты; включён мониторинг.

## Метрики успеха
- Успешная обработка платежей (конверсия >95%, низкая доля рефьюзов).
- Отсутствие двойных списаний (идемпотентность). Очередь без бэклога >15 мин.
- Стабильные FX-конверсии, кэш-хиты ≥80%.
- Покрытие тестами ≥80% модулей биллинга.

## Риски и меры
- Сбой FX API → фолбэк на кэш; алерт о деградации.
- Несоответствие подписей вебхука → немедленная блокировка операции, аудит-лог.
- Рост бэклога → горизонтальное масштабирование воркеров, увеличение Redis ресурсов.
- Ошибки миграции → откат по скрипту, окно обслуживания.

## Ветвление и релизы
- Рабочие ветки по фичам; PR с тестами и миграциями.
- На `main`: сборка Docker-образов, обновление changelog, релизные теги.
